[[concepts-context-and-schema]]
=== Context and schema

Two things bound what DICE extracts and what it will return: the `ContextId` that scopes a
proposition, and the schema that tells extraction what the domain looks like.

==== ContextId

Every proposition belongs to exactly one `ContextId`. It is the primary scope, and the starting
point of every query:

[source,java]
----
var query = PropositionQuery.againstContext("user:42");
----

There is no `PropositionQuery.create()`. That is a design decision, not an omission: without a
scope, "load everything" would be the shortest thing to write, and in a store that accumulates
indefinitely that is a production incident waiting to happen.

`ContextId` is a Kotlin value class, so it costs nothing at runtime. A Java query takes the id as a
plain string, as above. Java reads an id back with `getContextIdValue()`, which every public type
with a `contextId` property has.

[cols="2,3",options="header"]
|===
| Area | Types with `getContextIdValue()`

| Propositions and queries
| `Proposition`, `PropositionQuery`, `SourceAnalysisContext`

| Events
| `UngroundedMentionsFound`, `PropositionContradicted`

| Incremental analysis
| `BookmarkKey`, `HashKey`, `ProcessedChunkRecord`

| Memory maintenance
| `DreamLoopReport`, `CollectorRunContext`, `CollapseUndoCommand`

| Extraction runs
| `ExtractionRun`, `ExtractionRunKey`

| Schema drift
| `DriftReport`, `DriftCheckResult` (`null` when the check covered the whole graph)
|===

`CollapseUndoContextMismatchException` names two contexts, read with
`getCommandedContextIdValue()` and `getActualContextIdValue()`.

[source,java]
----
CollapseUndoCommand command = CollapseUndoCommand.of("acme", survivorId, retiredId);
try {
    CollectorSignalsKt.undoSingleCollapse(command, traceQuery, propositions, collectorRecords);
} catch (CollapseUndoContextMismatchException mismatch) {
    log.warn("Undo for context {} refused: proposition {} belongs to {}",
            mismatch.getCommandedContextIdValue(), mismatch.getPropositionId(),
            mismatch.getActualContextIdValue());
}
----

Kotlin reads the typed properties.

[source,kotlin]
----
val command = CollapseUndoCommand(ContextId("acme"), survivorId, retiredId)
try {
    undoSingleCollapse(command, traceQuery, propositions, collectorRecords)
} catch (mismatch: CollapseUndoContextMismatchException) {
    log.warn("Undo for context {} refused: proposition {} belongs to {}",
        mismatch.commandedContextId.value, mismatch.propositionId, mismatch.actualContextId.value)
}
----

What a context should represent is your decision. Common choices: one per user, one per tenant, one
per conversation, one per document collection. Contexts do not nest; if you need a hierarchy, encode
it in the value and query by prefix at your own layer.

Four types that a caller builds take a `ContextId` in their constructor. Java builds them with a
static `of(...)` that takes the id as a string.

[source,java]
----
BookmarkKey bookmark = BookmarkKey.of("acme", "conversation-1");
HashKey hash = HashKey.of("acme", contentHash);
CollectorRunContext run = CollectorRunContext.of("run-1", "acme");
CollapseUndoCommand command = CollapseUndoCommand.of("acme", survivorId, retiredId);
----

Kotlin calls the constructors.

[source,kotlin]
----
val bookmark = BookmarkKey(ContextId("acme"), "conversation-1")
----

==== SourceAnalysisContext

`SourceAnalysisContext` is the per-run configuration handed to the pipeline. It carries the schema,
the resolver, the `ContextId`, and everything else extraction needs to know:

[cols="1,3", options="header"]
|===
| Field | Purpose

| `schema`
| The `DataDictionary` describing your domain's entity types.

| `entityResolver`
| How mentions become entities. See <<concepts-entity-resolution>>.

| `contextId`
| The scope everything extracted lands in.

| `knownEntities`
| Entities the run should already recognise — `KnownEntity.asCurrentUser(user)` is the common case.

| `relations`
| Declared predicates, used by extraction and by relation-based graph projection.

| `promptVariables`
| Extra values available to the extraction template.

| `sourceLocator`
| How to get back to the source material, for provenance.

| `perspective`
| Whose point of view the text is written from.

| `mintNewEntities`
| Whether unresolved mentions may create entities. Off by default.

| `mintedEntityProperties`
| Properties stamped onto anything minted.
|===

It is a data class with `with*` builders, so a base context can be specialised per run:

[source,java]
----
var context = SourceAnalysisContext
        .withContextId("user:42")
        .withEntityResolver(resolver)
        .withSchema(dataDictionary)
        .withKnownEntities(KnownEntity.asCurrentUser(user))
        .withRelations(relations)
        .withMintNewEntities(true)
        .withSourceLocator(sourceLocator);
----

==== The DataDictionary and SchemaAdherence

The `DataDictionary` is your domain's schema: the entity types extraction should look for, and the
relationship metadata that names the predicates it may use. `SchemaRegistry` holds them.

`SchemaAdherence` decides how strictly extraction obeys it. Two independent switches:

[cols="1,1,1,2", options="header"]
|===
| Constant | `entities` | `predicates` | Behaviour

| `SchemaAdherence.STRICT`
| `true`
| `true`
| Only schema entity types, only schema predicates. Nothing outside the model gets in.

| `SchemaAdherence.DEFAULT`
| `true`
| `false`
| Entity types locked to the schema; any predicate allowed. The usual choice.

| `SchemaAdherence.RELAXED`
| `false`
| `false`
| Schema types preferred but not required, on both axes. Use when you are still discovering the
  domain.
|===

Set it on the extractor:

[source,java]
----
LlmPropositionExtractor.withLlm(llmOptions)
        .withAi(ai)
        .withPropositionRepository(repository)
        .withSchemaAdherence(SchemaAdherence.STRICT);
----

To keep the builder in a variable, for example to choose the `Ai` later, start from `builder`. It
returns `LlmPropositionExtractorBuilder`, a top-level type.

[source,java]
----
LlmPropositionExtractorBuilder builder = LlmPropositionExtractor.builder(llmOptions);
LlmPropositionExtractor extractor = builder.withAi(ai);
----

[source,kotlin]
----
val builder = LlmPropositionExtractor.builder(llmOptions)
val extractor = builder.withAi(ai)
----

Strictness is the main lever on extraction noise. Start at `DEFAULT`; move to `STRICT` when you
trust the schema and want the extractor to stop inventing predicates; move to `RELAXED` only while
exploring.

==== Relations

`Relations` declares the predicates that may hold between entities. Extraction uses them to phrase
claims consistently, and `RelationBasedGraphProjector` uses them to decide which edges to create.
Declaring relations is what turns free-text claims into a graph you can traverse rather than a bag
of sentences.

.Try it now
[source,java]
----
var strict = SourceAnalysisContext
        .withContextId("strict-test")
        .withEntityResolver(resolver)
        .withSchema(dataDictionary);
// ... run the same chunk through an extractor built with STRICT and with RELAXED,
// and compare how many propositions and mentions survive.
----
The gap between the two is the size of the noise your schema is currently suppressing.
