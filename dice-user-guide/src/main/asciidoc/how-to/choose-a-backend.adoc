[[how-to-choose-a-backend]]
=== Choose a storage backend

*Prerequisites*: a DICE starter on the classpath. `dice-starter` gives you the in-memory stores and
`dice-starter-neo4j` gives you the Drivine stores on Neo4j. Both bring in `dice-storage-autoconfigure`.

The starter you add is what decides. With `dice-starter-neo4j` on the classpath, DICE looks at what
your application sets up: when Drivine is configured, it uses its Drivine stores, and when it isn't,
it uses its in-memory stores. You don't set a property for that. The code you write against
`PropositionRepository` is the same either way.

Drivine counts as configured when your application has a Drivine `PersistenceManager` bean. With
`dice-starter-neo4j` you don't write that bean yourself: once Drivine has a data source, DICE builds
it for you. Which database it talks to is decided by Drivine's own configuration, not by DICE.

Without `dice-starter-neo4j`, DICE keeps its in-memory stores, just as it always has, even if your
application uses Drivine for its own data. It builds no Drivine managers for you and writes no schema
to your database. Without the starter, DICE wires its Drivine stores only when you set the
deprecated `embabel.dice.store.type=graph`, and then they run on the `PersistenceManager` and
`StatelessGraphObjectManager` your application defines.

[cols="1,2,3", options="header"]
|===
| Backend | How you get it | Choose it when

| In-memory
| The default. Add `dice-starter`, or add `dice-starter-neo4j` and give Drivine no data source.
| Development, tests, single-process applications, and anything where losing the store on restart is
  acceptable. Needs an `Ai` bean for embeddings.

| JSON file
| Define a `JsonFilePropositionRepository` bean yourself.
| You want survival across restarts with no infrastructure at all. Not for concurrent writers.

| Graph (Drivine/Neo4j)
| Add `dice-starter-neo4j` and one entry under `database.datasources`.
| Production. Durable, concurrent, with native graph traversal, a vector index, and decay applied in
  the database.
|===

SQLite will get a starter of its own in a later release.

==== Switching to the graph backend

First, import the `dice-dependencies` BOM so every DICE module and Drivine stay on versions that
work together, then swap `dice-starter` for `dice-starter-neo4j`. The BOM supplies the versions, so
the starter needs none:

[source,xml]
----
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>com.embabel.dice</groupId>
            <artifactId>dice-dependencies</artifactId>
            <version>${dice.version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

<dependencies>
    <dependency>
        <groupId>com.embabel.dice</groupId>
        <artifactId>dice-starter-neo4j</artifactId>
    </dependency>
</dependencies>
----

The Neo4j starter brings in `dice-storage` and Drivine's Spring Boot starter, which comes with the
Neo4j driver. The BOM doesn't manage Spring Boot itself; that stays with your application.

Then declare a data source. This is Drivine's configuration, and its `type` and connection settings
pick the database:

[source,yaml]
----
database:
  datasources:
    neo:
      type: NEO4J
      host: localhost
      port: 7687
      username: neo4j
      password: ${NEO4J_PASSWORD}
      database-name: neo4j
----

That's all. You define no beans. Drivine builds its factories from the data source, and DICE builds
the `PersistenceManager` and `StatelessGraphObjectManager` from them. With that `PersistenceManager`
in place, the auto-configuration swaps `PropositionRepository`, `ChunkHistoryStore`, `DecayManager`,
`ProjectionRecordStore` and `CollectorRecordStore` for their Drivine equivalents, and registers the
schema catalogues that create the constraints and, when an embedding model is available, the vector
index. See <<features-vector-index>> for models added after startup. Take the data source away and
DICE goes back to its in-memory stores.

If you have several data sources, tell DICE which one to keep its stores in:

[source,yaml]
----
embabel:
  dice:
    store:
      datasource: neo
----

With several data sources and none named, or with a name Drivine doesn't have, startup stops and
lists the data sources that are configured. With only one, you can leave the property out.

If your configuration still sets `embabel.dice.store.type`, you can remove it once
`dice-starter-neo4j` is on the classpath. It is deprecated, and <<reference-configuration-properties>>
lists what each value still does. Don't remove `graph` without adding the starter, though: without
it, DICE would go back to its in-memory stores.

See <<features-graph-storage>> for the full activation detail.

==== What changes when you switch

[cols="1,1,1", options="header"]
|===
| | In-memory | Graph

| Survives restart
| No
| Yes

| Concurrent writers
| Single process
| Yes

| Vector search
| Through the `Ai` embedding service
| Native Neo4j vector index

| Graph traversal
| Default implementations over the primitives
| Native Cypher, via `GraphQueryCapable`

| Decay tick
| In-process, over the whole store
| Executed in the database

| Extra infrastructure
| None
| A Neo4j instance
|===

==== Using your own Drivine beans

This is for apps with `dice-starter-neo4j`. You only need it when DICE's choice of Drivine beans
doesn't suit you, for example when the `PersistenceManager` should come from somewhere other than one
of Drivine's factories. Define both
beans yourself, on the same database, and DICE uses them instead of building its own. Define only one
and startup fails: DICE never builds one manager to sit beside yours, because the two could end up on
different databases. The exception is an app that still sets `embabel.dice.store.type=graph`. There
DICE builds neither manager, so startup works if your own beans cover every store that needs the
missing one, and otherwise fails because that bean doesn't exist.

[source,java]
----
@Configuration
public class DrivineConfig {

    @Bean
    PersistenceManager persistenceManager(PersistenceManagerFactory factory) {
        return factory.get("neo");
    }

    @Bean
    StatelessGraphObjectManager graphObjectManager(GraphObjectManagerFactory factory) {
        return factory.stateless("neo");
    }
}
----

==== Overriding the choice entirely

Every auto-configured bean is `@ConditionalOnMissingBean`. Define your own `PropositionRepository`
and the auto-configuration steps aside — which is also how you implement `PropositionStore` against
a backend DICE does not ship.

Implement only the capabilities you genuinely support. The default implementations on
`VectorSearchCapable`, `GraphTraversalCapable`, `GraphQueryCapable` and `TemporalQueryCapable`
express each operation over the base primitives, so an unimplemented capability degrades in
performance rather than breaking.

==== Migrating between backends

There is no shipped migration tool. Propositions are the system of record and everything else is a
projection, so a migration is: read every proposition and entity from the old store, write them to
the new one, then re-project. Reconciliation is idempotent, so re-projecting is safe to repeat.
