[[how-to-analyze-conversations]]
=== Analyse a conversation incrementally

*Prerequisites*: `dice`, a configured LLM, a `PropositionRepository` and a `ChunkHistoryStore`.

A conversation is not a document. It arrives a turn at a time, the same claim gets restated and
revised, and the user themselves is an entity the extractor should already know about.

==== The incremental analyser

`IncrementalAnalyzer` processes an `IncrementalSource` and remembers what it has already seen.
`ConversationSource` wraps a conversation; `ConversationSegmenter` decides where one unit of analysis
ends and the next begins, so a claim spanning three turns is not cut in half.

[source,java]
----
var source = new ConversationSource(conversation);
var result = analyzer.analyze(source, context);
result.persist(propositionRepository, entityRepository);
----

Re-analysing the same conversation is cheap: `ChunkHistoryStore` reports what has already been
processed and the analyser skips it.

==== Tell the context who is talking

Without this, "I prefer the early recordings" produces a claim about nobody.

[source,java]
----
var context = SourceAnalysisContext
        .withContextId(user.currentContext())
        .withEntityResolver(entityResolverForUser(user))
        .withSchema(dataDictionary)
        .withRelations(relations)
        .withKnownEntities(KnownEntity.asCurrentUser(user));
----

`KnownEntity.asCurrentUser(...)` is the important line: it gives the resolver a first-class identity
for the speaker, so first-person claims attach to them.

==== Drive it from events

Conversation analysis costs an LLM call, so it should not sit in the request path.
`ConversationAnalysisRequestEvent` exists for exactly this:

[source,java]
----
@Async
@Transactional
@EventListener
public void onConversationExchange(ConversationAnalysisRequestEvent event) {
    var context = SourceAnalysisContext
            .withContextId(event.user.currentContext())
            .withEntityResolver(entityResolverForUser(event.user))
            .withSchema(dataDictionary)
            .withRelations(relations)
            .withKnownEntities(KnownEntity.asCurrentUser(event.user));

    var source = new ConversationSource(event.conversation);
    var result = analyzer.analyze(source, context);

    result.persist(propositionRepository, entityRepository);
}
----

`SourceAnalysisRequestEvent` is the general form for non-conversation sources.

==== Turn on revision

In a conversation the same thing gets said repeatedly, and sometimes retracted. Without revision you
accumulate near-duplicates; with it, restatements reinforce and reversals are classified as
contradictions.

[source,java]
----
var pipeline = PropositionPipeline
        .withExtractor(extractor)
        .withRevision(reviser, propositionRepository);
----

Revision compares against what is already stored and classifies each new claim as new, merged,
reinforced or contradicted. It still persists nothing — `hasRevision` tells you which set
`propositionsToPersist()` will return.

A restatement that names a source reinforces a stored claim only when the stored claim does not
already hold that source. A source is a grounding id, a provenance entry or a source id.
A restatement that names no source still reinforces. Processing the same chunk again, with the
same chunk id and text, leaves the stored claim unchanged: the result is still merged or
reinforced, its `revised` equals its `original`, and `isReplay()` returns true. Revision
statistics leave replays out of their counts, and `replayedCount` on the chunk or run result says
how many there were, so a retried run shows up as replays.

[source,java]
----
ChunkPropositionResult result = pipeline.processChunk(chunk, context);
long replays = result.getRevisionResults().stream().filter(RevisionResult::isReplay).count();
int sameNumber = result.getReplayedCount();
----
 When two chunks in one run restate the same
stored claim, the second builds on the first, so the saved claim keeps both sources.

==== When a write fails

`IncrementalPropositionExtraction` records a window as processed only after its claims are stored.
If the store fails, the window stays unrecorded, and the next event for the same source analyses
again from the same starting point. The window may end later if the source has grown since. One
failure is the exception: with no writer bound, a failure at the run link step after the claims are
saved records the window and is still thrown. Projection and grounding run after the window is
recorded. An exception thrown by projection or grounding reaches the caller. A failure those
services only count, such as a failed relationship write or a failed grounding edge, does not.

`analyze` records the window before it returns, so in the example above a failed
`result.persist(...)` leaves the window recorded and it is not analysed again. If you store the
result yourself and need the window to stay unrecorded when the write fails, use
`IncrementalPropositionExtraction`, or keep the chunk history store in the same transaction as the
write.

`extractPropositions` drains the events that are queued, then throws the first failure it saw. Every
exception it throws is unchecked. After the first failure the drain finishes only the events queued
at that moment, and events queued later wait for the next call. A failure while building the context
or analysing a window is logged, and that window is retried on the next event. A
`LineageNotRecordedException` is always thrown, also when it comes before the store step. If the
thread's interrupt flag is set, the drain stops and the events still queued wait for the next call. A
store or pipeline that catches an interrupt must set the flag again, as is the Java convention.

A failure that reaches the caller lets a host transaction roll back. For one-time processing, keep the
chunk history in the same transactional store as the claims. The Drivine stores do this. Call
`extractPropositions` inside a transaction. Without a transaction, a write that fails part way is
retried, and the retry can add the window's claims again.

==== Scope per user

Give each user their own `ContextId`. It is the boundary that keeps one user's beliefs out of
another's retrieval, and it is what makes "forget everything about me" a bounded operation.
