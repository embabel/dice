[[how-to-analyze-conversations]]
=== Analyse a conversation incrementally

*Prerequisites*: `dice`, a configured LLM, a `PropositionRepository` and a `ChunkHistoryStore`.

A conversation is not a document. It arrives a turn at a time, the same claim gets restated and
revised, and the user themselves is an entity the extractor should already know about.

==== The incremental analyser

`IncrementalAnalyzer` processes an `IncrementalSource` and remembers what it has already seen.
`ConversationSource` wraps a conversation; `ConversationSegmenter` decides where one unit of analysis
ends and the next begins, so a claim spanning three turns is not cut in half.

[source,java]
----
var source = new ConversationSource(conversation);
var result = analyzer.analyze(source, context);
result.persist(propositionRepository, entityRepository);
----

Re-analysing the same conversation is cheap: `ChunkHistoryStore` reports what has already been
processed and the analyser skips it.

==== Tell the context who is talking

Without this, "I prefer the early recordings" produces a claim about nobody.

[source,java]
----
var context = SourceAnalysisContext
        .withContextId(user.currentContext())
        .withEntityResolver(entityResolverForUser(user))
        .withSchema(dataDictionary)
        .withRelations(relations)
        .withKnownEntities(KnownEntity.asCurrentUser(user));
----

`KnownEntity.asCurrentUser(...)` is the important line: it gives the resolver a first-class identity
for the speaker, so first-person claims attach to them.

==== Drive it from events

Conversation analysis costs an LLM call, so it should not sit in the request path.
`ConversationAnalysisRequestEvent` exists for exactly this:

[source,java]
----
@Async
@Transactional
@EventListener
public void onConversationExchange(ConversationAnalysisRequestEvent event) {
    var context = SourceAnalysisContext
            .withContextId(event.user.currentContext())
            .withEntityResolver(entityResolverForUser(event.user))
            .withSchema(dataDictionary)
            .withRelations(relations)
            .withKnownEntities(KnownEntity.asCurrentUser(event.user));

    var source = new ConversationSource(event.conversation);
    var result = analyzer.analyze(source, context);

    result.persist(propositionRepository, entityRepository);
}
----

`SourceAnalysisRequestEvent` is the general form for non-conversation sources.

==== Turn on revision

In a conversation the same thing gets said repeatedly, and sometimes retracted. Without revision you
accumulate near-duplicates; with it, restatements reinforce and reversals are classified as
contradictions.

[source,java]
----
var pipeline = PropositionPipeline
        .withExtractor(extractor)
        .withRevision(reviser, propositionRepository);
----

Revision compares against what is already stored and classifies each new claim as new, merged,
reinforced or contradicted. It still persists nothing — `hasRevision` tells you which set
`propositionsToPersist()` will return.

A restatement that names a source reinforces a stored claim only when the stored claim does not
already hold that source. A source is a grounding id, a provenance entry or a source id.
A restatement that names no source still reinforces. Processing the same chunk again, with the
same chunk id and text, leaves the stored claim unchanged: the result is still merged or
reinforced, its `revised` equals its `original`, and `isReplay()` returns true. Revision
statistics leave replays out of their counts, and `replayedCount` on the chunk or run result says
how many there were, so a retried run shows up as replays.

[source,java]
----
ChunkPropositionResult result = pipeline.processChunk(chunk, context);
long replays = result.getRevisionResults().stream().filter(RevisionResult::isReplay).count();
int sameNumber = result.getReplayedCount();
----
 When two chunks in one run restate the same
stored claim, the second builds on the first, so the saved claim keeps both sources.

==== When a write fails

`IncrementalPropositionExtraction` records a window as processed only after its claims are stored.
If the store fails, the window stays unrecorded, and the next event for the same source analyses
again from the same starting point. The window may end later if the source has grown since. One
failure is the exception: with no writer bound, a failure at the run link step after the claims are
saved records the window and is still thrown. Projection and grounding run after the window is
recorded. An exception thrown by projection or grounding reaches the caller. A failure those
services only count, such as a failed relationship write or a failed grounding edge, does not.

`analyze` records the window before it returns. When the chunk history store commits on its own, a
failed `result.persist(...)` in the example above leaves the window recorded and it is not analysed
again. The example is `@Transactional`, so with a transactional chunk history store the record and
the write share one transaction, and a failed write that rolls the transaction back rolls the
record back too. Spring rolls back on an unchecked exception by default, not on a checked one. If
you store the
result yourself and need the window to stay unrecorded when the write fails, use
`IncrementalPropositionExtraction`, or keep the chunk history store in the same transaction as the
write.

`extractPropositions` runs the caller's event on the caller's thread and throws its failure. Every
exception it throws is unchecked. A call from another thread waits for the running one to finish
instead of handing its event over, so one caller's failure never rolls back another caller's work.
A published `SourceAnalysisRequestEvent` is handed to a single thread DICE owns, and the publisher
returns at once. Its queue holds 1,000 events; one it cannot take is logged at `error` and dropped,
and the next event for the source analyses the window again. If your application defines exactly
one `TaskDecorator` bean, each event is decorated with it on the publisher's thread, so a context it
carries, such as a tenant, reaches the extraction. For any other decorator, or to size the queue
yourself, bind your own executor before the first event:

[source,java]
----
ThreadPoolTaskExecutor events = new ThreadPoolTaskExecutor();
events.setCorePoolSize(1);
events.setMaxPoolSize(1);
events.setQueueCapacity(500);
events.setTaskDecorator(tenantDecorator);
events.initialize();
extraction.withEventExecutor(events);
----

Give extraction an executor of its own. If a running extraction waits on the same executor, for
example through concurrent chunk extraction, the two can wait for each other forever. When the
Spring context closes, `close()` gives DICE's own queued events 30 seconds to finish.
A call made from inside a running extraction on the same thread, such as from a save listener, is
queued and run after the current window is recorded. After the first failure only the events queued
at that moment run. A failure while building the context
or analysing a window is logged, and that window is retried on the next event. A
`LineageNotRecordedException` that reaches the drain is thrown, also when it comes before the store
step. One thrown by a provider while the context is built is logged like any other provider failure.
Callers waiting for the lock run in the order they arrived. A direct call waits at most 30 seconds
and then throws `ExtractionBusyException`. Nothing of its event was stored, so roll back and try
again later. The limit exists because a caller inside a transaction may hold a database lock the
running extraction needs, which on SQLite is the whole file's write lock.
If the thread's interrupt flag is set, the run stops and the events still queued are dropped. If the
caller's own event never ran, because the thread was interrupted before or while it waited, the call
throws a `CancellationException` and the flag stays set, so a surrounding transaction can roll back.
The next event for the same source analyses the window again. A store or pipeline that catches an interrupt must set the flag again, as is the Java convention.

A failure that reaches the caller lets a host transaction roll back. To make a failed write leave no
trace, keep the chunk history in the same transactional store as the claims, as the Drivine stores
do, and call `extractPropositions` inside a transaction. Without a transaction, a write that fails
part way is retried, and the retry can add the window's claims again.

A transaction alone does not stop two callers from analysing the same window. DICE releases its lock
when `extractPropositions` returns, before the host commits, so a second transaction can still read
the old bookmark. If two transactions can extract from the same source at once, serialize them
through the commit, for example with one worker per source.

A window whose store or record step fails is logged at `error` with its source, its context and its
item range, and the exception is attached. The same source and start index logged on every event
means the window fails every time, so the source makes no progress and each event pays for the
analysis again. The end of the range can grow with the source until the window is full. To stop that, stop publishing events for the source until the cause is fixed.

==== Scope per user

Give each user their own `ContextId`. It is the boundary that keeps one user's beliefs out of
another's retrieval, and it is what makes "forget everything about me" a bounded operation.
