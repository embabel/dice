[[features-graph-storage]]
=== Graph-backed storage

*Activation*: `dice-starter-neo4j` or `dice-starter-sqlite` is on the classpath and Drivine is
configured. Give the starter one data source and DICE builds the `PersistenceManager` bean.
With neither starter, DICE uses its in-memory stores by default. The deprecated
`embabel.dice.store.type=graph` still enables explicitly configured Drivine stores.

*Availability*: Both starters bring in `dice-storage`, `dice-storage-autoconfigure` and Drivine
from DICE {dice-version}. Use a Neo4j instance or a local SQLite file.

==== When to use it

Use Neo4j when you need a shared database or a native vector index.
SQLite provides durable local storage and serializes writes. Use the default in-memory backend
when you can discard the state on restart, such as in many development and test setups.

==== Impact

* *Infrastructure*: Drivine connects to a Neo4j instance or opens a local SQLite file through JDBC.
* *Latency*: database queries replace in-memory lookups. Neo4j queries make network round trips.
* *Memory*: propositions no longer live in your heap.
* *LLM calls*: unchanged.
* *Startup*: schema catalogues create constraints. On Neo4j they also create the vector index when
  an embedding model is available. See <<features-vector-index>> for models added after startup.

==== How to enable

Add the starter for your backend and import the `dice-dependencies` BOM for the versions. Configure
one data source under `database.datasources`. The `type` and connection settings choose the database.
Drivine builds its factories from the data source. DICE builds the `PersistenceManager` and
`StatelessGraphObjectManager` from those factories, after Drivine's
auto-configuration and before its own storage auto-configuration, so the storage auto-configuration
sees them when it decides. <<how-to-choose-a-backend>> walks through it.

With several data sources, set `embabel.dice.store.datasource` to the one DICE should use. If there
are several and none is named, or the name isn't one Drivine has, startup stops and lists the
configured ones.

DICE builds the `PersistenceManager` and `StatelessGraphObjectManager` as a pair, and only when your
application defines neither. Define both yourself, on the same database, and DICE builds nothing and
uses yours. Define only one and startup fails, because DICE would otherwise save through one database
and read back through another; the message asks you to define both or neither.

If your own auto-configuration registers the `PersistenceManager` after DICE's, DICE can't see it in
time. Rather than run with any of its stores in memory while Drivine is configured, startup fails and
names the stores that were left in memory. That covers every DICE store with a Drivine version, not
only the proposition store. You can still swap any one store by defining your own bean of that type;
the check leaves your bean alone, and the rest must still follow Drivine. To fix the failure, order
your auto-configuration before `DiceStorageAutoConfiguration`, or define the store beans yourself.

Without a `PersistenceManager` bean, DICE uses its in-memory stores. The deprecated
`embabel.dice.store.type` property can still force `in-memory` while Drivine is present; see
<<reference-configuration-properties>>.

Automatic detection requires one of the two Drivine starters. An application that uses
Drivine for its own data and has neither starter keeps DICE's in-memory stores, as before. DICE
builds no Drivine managers for it, doesn't check its store choice against Drivine, and writes no
schema to its database. Such an application can still set `embabel.dice.store.type=graph`, and DICE
then uses its Drivine stores on the `PersistenceManager` and `StatelessGraphObjectManager` the
application defines itself.

==== What you get

When DICE uses its Drivine stores, `DiceStorageAutoConfiguration` provides:

[cols="1,2", options="header"]
|===
| Bean | Implementation

| `PropositionRepository`
| `DrivinePropositionRepository` — requires an `Ai` bean for embeddings

| `ChunkHistoryStore`
| `DrivineChunkHistoryStore`

| `DecayManager`
| `GraphDecayManager` — decay executed in the database

| `ProjectionRecordStore`
| `DrivineProjectionRecordStore` — edge lineage

| `CollectorRecordStore`
| `DrivineCollectorRecordStore` — reclamation audit trail

| `SchemaCatalog` beans
| Proposition constraints, lineage-record schema, and the Neo4j vector index spec
|===

Every one is `@ConditionalOnMissingBean`, so your own bean always wins.

==== The graph model

`dice-storage` maps propositions onto typed nodes: `PropositionNode`, `SourceNode`,
`ProcessedChunkNode`, `Mention` and `DerivedFrom`, with `PropositionView` and
`PropositionWithProvenanceView` as the read projections. `PropositionGraphMapper` handles the
mapping; `GraphProjectionCypher` holds the traversal queries.

==== Example

Nothing in your code changes. This is the same call against either backend:

[source,java]
----
var confident = propositionRepository.query(
        PropositionQuery.againstContext(contextId).withMinEffectiveConfidence(0.7));
----

What changes is that on the graph backend the repository also implements `GraphQueryCapable`, so
native traversal is available:

[source,java]
----
if (propositionRepository instanceof GraphQueryCapable g) {
    var neighbourhood = g.neighborhood(entityId, 2);
}
----
