[[features-graph-storage]]
=== Graph-backed storage

*Activation*: `embabel.dice.store.type=graph`

*Availability*: `dice-storage` and `dice-storage-autoconfigure`, from DICE {dice-version}. Costs a
Neo4j instance.

==== When to use it

Use it in production, and whenever you need any of: durability across restarts, more than one
process writing, native graph traversal, or decay applied in the database rather than in your heap.

Leave it off for development, tests and single-process applications. The in-memory backend is the
default precisely because most of what you do while building DICE into an application does not need
Neo4j.

==== Impact

* *Infrastructure*: a Neo4j instance, reached through Drivine (`drivine4j-spring-boot-starter`).
* *Latency*: network round trips replace map lookups. Traversals get much faster; single-id lookups
  get slower.
* *Memory*: propositions no longer live in your heap.
* *LLM calls*: unchanged.
* *Startup*: schema catalogues create constraints and, when an embedding model is available, the
  vector index. See <<features-vector-index>> for models added after startup.

==== How to enable

[source,yaml]
----
embabel:
  dice:
    store:
      type: graph
----

Plus Drivine's Neo4j connection configuration.

==== What you get

With `type=graph`, `DiceStorageAutoConfiguration` provides:

[cols="1,2", options="header"]
|===
| Bean | Implementation

| `PropositionRepository`
| `DrivinePropositionRepository` — requires an `Ai` bean for embeddings

| `ChunkHistoryStore`
| `DrivineChunkHistoryStore`

| `DecayManager`
| `GraphDecayManager` — decay executed in the database

| `ProjectionRecordStore`
| `DrivineProjectionRecordStore` — edge lineage

| `CollectorRecordStore`
| `DrivineCollectorRecordStore` — reclamation audit trail

| `SchemaCatalog` beans
| Proposition constraints, lineage-record schema, and the vector index spec
|===

Every one is `@ConditionalOnMissingBean`, so your own bean always wins.

==== The graph model

`dice-storage` maps propositions onto typed nodes: `PropositionNode`, `SourceNode`,
`ProcessedChunkNode`, `Mention` and `DerivedFrom`, with `PropositionView` and
`PropositionWithProvenanceView` as the read projections. `PropositionGraphMapper` handles the
mapping; `GraphProjectionCypher` holds the traversal queries.

==== Example

Nothing in your code changes. This is the same call against either backend:

[source,java]
----
var confident = propositionRepository.query(
        PropositionQuery.againstContext(contextId).withMinEffectiveConfidence(0.7));
----

What changes is that on the graph backend the repository also implements `GraphQueryCapable`, so
native traversal is available:

[source,java]
----
if (propositionRepository instanceof GraphQueryCapable g) {
    var neighbourhood = g.neighborhood(entityId, 2);
}
----

==== On SQLite

The graph stores also run on Drivine's SQLite backend, a single file in place of a Neo4j instance.
SQLite has one write lock per file, which shapes these rules:

* The data source's transactions must take the write lock as they begin. Drivine's own SQLite
  provider does this. Startup refuses a data source whose transactions do not, or whose transaction
  mode cannot be read.
* A host transaction manager can share the file with Drivine in one way only: Drivine reads the
  manager's data source through Spring's `TransactionAwareDataSourceProxy`, so both use the same
  connection. Startup refuses any other sharing, such as one pool used directly by both, or two
  pools over the same file.
* A save embeds its text before it takes the lock. Outside a transaction, a save that repeats a
  stored fact is answered from reads alone. Inside a caller's SQLite transaction, an exact replay
  still calls the embedder.
* `reembedAll` inside a caller's transaction reads the vector index on a connection of its own, so
  it needs a pool of at least two connections. With one, it is refused.
