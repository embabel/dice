[[features-audit-history]]
=== Proposition audit history

*Activation*: Register the `DiceStorageSchema` returned by `AuditLogSchema.forRegistration()`
and add it to a Drivine `SchemaCatalog` targeted at the proposition datasource. Construct a
`DrivineAuditLogStore` and wrap the repository with `AuditingPropositionRepository.wrapping(...)`.

*Availability*: `dice` provides the audit APIs. `dice-storage` persists history on Neo4j and SQLite.

[WARNING]
====
Experimental. The API may change before 1.0.
====

The application authorizes access to each context and routes all proposition writes through the
audited repository. Use the direct manager returned by `PersistenceManagerFactory.get(datasource)`
and the same Spring transaction manager as the proposition repository. For schema registration and
transaction behavior, see the
https://github.com/embabel/dice/blob/main/docs/design/durable-audit-history.md[Drivine audit setup].

==== Establish coverage

Fence every writer to the context during cutover. Pause writers that still use the original
repository. Take a complete snapshot under the audit fence, including propositions in non-active
states. Resume writes through the audited repository.

[source,java]
----
var audit = new DrivineAuditLogStore(
        persistenceManagerFactory.get(datasource), transactionManager);
var audited = AuditingPropositionRepository.wrapping(
        repository, audit, attributionProvider, AuditFailurePolicy.FAIL_WRITE,
        repository.auditCanonicalLookup());

audit.duringWrite(contextId, () -> {
    var cutover = Instant.now();
    var snapshot = repository.query(PropositionQuery.againstContext(contextId));
    audit.initializeBaseline(contextId, cutover, snapshot);
    return null;
});
----

Pass an empty snapshot only after verifying that the context contains no propositions.

==== Read recorded and historical state

Use `history(contextId, propositionId)` for the records of one proposition. Use
`beliefSetAsOf(contextId, instant)` to reconstruct the context at any covered instant in
transaction time.
Call historical queries outside any host transaction for a committed view.

Replay covers text, lifecycle status, raw confidence, importance, pinning and temporal metadata.
The live repository provides grounding, provenance and the metadata map for the current
proposition. For a covered instant, `asOf(contextId, propositionId, instant)` returns `null` if
the proposition was absent.
Historical queries throw `AuditCoverageException` when the requested instant predates the
baseline, exceeds the observed horizon or lacks a complete audit trail.

[[features-world-progression]]
==== Record a confirmed world change on SQLite

Use `SqliteWorldProgression` when the application accepts a change with an effective date.
For example, a billing event says an account moved from Pro to Basic at midnight. Supply the
current Pro proposition, the Basic proposition with its source, and the billing event's stable ID.

Set `embabel.dice.store.world-progression.enabled=true` on every instance that opens this SQLite
database with the DICE starter. With custom schema catalogs, omit the unique constraint on
`(contextId, text)` and keep the unique proposition ID. After schema enforcement, call
`enable` before accepting work. The first call removes the legacy text constraint from an
existing database. Schedule that step while writes are stopped and keep a database backup.

[source,java]
----
var progression = SqliteWorldProgression.enable(repository, audit, attributionProvider);
var basic = progression.record(event.id(), currentPro, acceptedBasic, event.effectiveAt());
----

Here `repository` is the SQLite `DrivinePropositionRepository` and `audit` is the
`DrivineAuditLogStore` for the same datasource and transaction manager. The ordinary
deduplicating write path still uses exact text. When a fact returns, a new occurrence gets
its own ID and an ordinary save of that text attaches to the active occurrence. Upgrade all
writers before enabling this policy. To roll back to a release that enforces unique text,
restore the pre-migration backup or reconcile repeated occurrences before restoring that constraint.

DICE stores Pro as `SUPERSEDED` with `validTo` set to the effective instant. Basic starts at
the same instant and links to Pro in `supersedes`. Both writes and their audit records commit
together. A second delivery of the same event returns the stored successor. A stale
predecessor, a pinned claim, or an event ID reused for another transition rejects the write.

Keep source disagreements on the existing revision path. Historical `CONTRADICTED` rows
stay as recorded.

For valid-time reads, open a scoped repository view for the authorized context. Include
`ACTIVE` and `SUPERSEDED` propositions and evaluate their validity intervals to select the
occurrence for the effective date. For transaction-time reads, use the complete audit
baseline described above. A change effective Monday and recorded Wednesday appears in
valid time from Monday and in the audit timeline from Wednesday.
