[[overview-modules]]
=== Modules

DICE publishes its artifacts under the `com.embabel.dice` group. Most applications need just a BOM and
one starter, and define no beans of their own.

[cols="1,2,1", options="header"]
|===
| Artifact | What it gives you | Pull it in when

| `dice-dependencies`
| A BOM that lines up every published DICE module and the Drivine version DICE is built against. It
  doesn't manage Spring Boot.
| Always. Import it in `dependencyManagement` and leave the versions off the DICE dependencies.

| `dice-starter`
| `dice` and `dice-storage-autoconfigure`, wired for the in-memory stores.
| You want DICE on Spring Boot without a database. This is the base of the other starters.

| `dice-starter-neo4j`
| `dice-starter` plus `dice-storage` and Drivine's Spring Boot starter, which brings the Neo4j driver.
  Add one entry under `database.datasources` and DICE uses its Drivine stores.
| You want propositions in Neo4j.

| `dice-starter-sqlite`
| `dice-starter` plus `dice-storage`, Drivine's Spring Boot starter and the SQLite JDBC driver.
  Add a SQLite data source under `database.datasources` and DICE uses its Drivine stores.
| You want propositions in a local SQLite file.

| `dice-starter-mcp`
| `dice-starter` plus `dice-mcp-autoconfigure` and the agent framework's MCP server module.
| You want DICE's tools exported over MCP.

| `dice`
| The whole domain: the `Proposition` model, the `PropositionStore` and `PropositionRepository`
  SPIs, the extraction pipeline, revision and conflict detection, entity resolution, the graph,
  Prolog and memory projectors, graph and discovery queries, incremental analysis, the in-memory and
  JSON-file stores, tuProlog integration, and the optional REST endpoints.
| Always. Everything else depends on it.

| `dice-storage`
| A Drivine implementation of `PropositionRepository`, `ChunkHistoryStore` and `DecayManager`.
| You want propositions in Neo4j or SQLite.

| `dice-storage-autoconfigure`
| Spring Boot auto-configuration: the Drivine stores when Drivine is configured and the in-memory
  ones otherwise, Drivine's `PersistenceManager` and `StatelessGraphObjectManager` built from its data
  source, the scheduled decay tick, and the multi-signal duplicate collector.
| You are on Spring Boot and assembling the modules yourself. The starters bring it in for you.

| `dice-report`
| Output projectors over propositions: rationale (why a fact is believed, with its evidence),
  structured reports, and surprising-link discovery.
| You need human-readable output.

| `dice-ingestion`
| An ingestion SPI turning artifacts into chunks, with a content-hash ledger so the same source is
  not extracted twice.
| You are feeding files or documents in, rather than conversation turns.

| `dice-metamodel`
| Schema governance for DICE knowledge graphs: content-hash stamping, the declared-schema contract,
  diffing, drift checking, and non-destructive quarantine.
| You want to check a graph's schema against what you declared. `dice-storage-autoconfigure` brings
  it in.

| `dice-mcp-autoconfigure`
| Spring Boot auto-configuration that exports DICE tools over MCP through the agent framework.
| You are assembling the modules yourself. `dice-starter-mcp` brings it in for you.

| `dice-store-conformance`
| Abstract JUnit suites, one for each store interface, that a backend's tests extend. See
  <<how-to-verify-a-backend>>.
| You are writing a storage backend and want its tests to check the documented behaviour of each
  store interface. Add it at test scope.
|===

`dice-integration-tests` is test-only: it holds the cross-feature end-to-end harness and is not
published for consumption.

.Dependency scope
[NOTE]
====
`embabel-agent-api` and `embabel-agent-rag-core` are declared `provided` in `dice`. Your application
brings the actual embabel-agent version at runtime; DICE only fixes the minimum it compiles against.
====
